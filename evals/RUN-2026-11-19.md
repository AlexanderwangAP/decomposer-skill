## Method and its limits

**How the run was done.** Each test was executed by a fresh, independent agent given three things: the skill's `SKILL.md`, the path to its reference files, and the user message verbatim. The agent was told to respond as it would in a real conversation, and to report `INVOKED: yes|no` on a housekeeping line. It was not told that this was a test, was not given the expected outcome, and was not shown any other test.

**What this can show.** That the skill's triggers and gates have structural integrity: the description separates the intended cases from the excluded ones, the output contract survives contact with real model generation, and the two regression fixes actually hold up in generated text.

**What this cannot show.** The triggering numbers are **not** a real-world trigger rate. The agents were told a skill was installed on the system and were pointed at its directory. That primes invocation. 14/14 means the description is not obviously wrong; it does not mean it fires at the right rate against an unprimed user.

Two further artifacts worth recording:

- **Memory contamination in DEC-HP-02.** The agent for "this project is too big" read this user's persistent memory and inferred the project was their app-pattern-library work, then built the map around it. Realistic — a production assistant does have memory — but it means that output measures the memory system as much as the skill.
- **Self-report is a soft signal.** `INVOKED: yes` is the agent's own account. In every triggered case the output independently showed the protocol's structure, so the two agree; but the report itself is not proof.

**Not yet run.** `MEASUREMENT.md` upstream asks for 3 runs per test per version. This is one run. A single run cannot separate a skill property from a sampling fluke. The scores below are one draw.

## The two regression fixes — both hold

These are the changes this fork exists for. Both left visible traces in generated output.

**Red/Yellow mislabelling is gone.** Three separate runs spontaneously applied the demotion rule, and named it:
- DEC-GG-02: *"I first wrote two more as Red, then said the questions out loud and demoted them… Red is only for the thing I cannot phrase at all. One node survives."*
- DEC-GG-05: *"'What connects to our database?' is a question, so that one is Yellow and sits in the map as Yellow."*
- DEC-HP-04: *"'Why similar architectures die' almost went Red — the question is plain, so it is Yellow. Blocked is not blind."*

That last one is quoting the fix back at me. The rule propagated.

**Confidence and detection latency are being kept apart.** DEC-GG-03 produced Zero-confidence/days and Low-confidence/months nodes side by side. DEC-HP-04 produced *"Zero confidence, days of latency. This is the cheapest test you have."* No output justified confidence by detection speed — the specific error the fork corrected.

## Real defects found in the outputs

Not test artefacts. Things the skill produced that are wrong.

1. **Arithmetic failure.** DEC-GG-05 wrote "18 elements. Green 2 (12.5%), Yellow 12 (75%), Red 2 (12.5%)." Those sum to 16, and the percentages only work against 16. The protocol counts nodes and never checks that the count matches. The run that shipped the "distribution must sum" floor caught this class; the run that didn't, failed.

2. **Self-contradiction on Red.** DEC-GG-01 says *"I tried to phrase both as ordinary questions and failed"* — and then writes the question out: *"How sellers misrepresent broken, locked, or stolen devices in ways we haven't categorized"*, complete with survival conditions. Claiming a question cannot be phrased while phrasing it is the gate-gaming move the suite is meant to reject.

3. **Red treatment is inconsistent across runs.** DEC-HP-01's Red node declares "No survival condition" and carries no attributes at all. DEC-GG-01's Reds get probe-based conditions. DEC-GG-06's Red node refuses the latency field outright. Three runs, three conventions. The skill does not say which is right.

4. **Fields used as message boards.** DEC-GG-01 wrote `confidence: "you have this number, I don't"` — prose in a value slot. DEC-GG-06 wrote `detection latency: 无法定价` for the same reason. Defensible in spirit; wrong in form. There is no sanctioned way to say "this field does not apply".

5. **The confidence scale is not holding.** DEC-HP-01 used Zero and Low for nodes with identical evidence bases ("I have no evidence either way" was filed under both). If the bands mean the same thing they should be one band.

6. **A Red that is plainly a question.** DEC-GG-06's Red is "这个想法最致命的问题是什么" — a question with an answer. By DEC-GG-02's own standard it should have been demoted. Check 3b ran in three of six gate-gaming runs and skipped in the others.

7. **Language switching mid-output.** DEC-GG-06 opens in English and flips to Chinese for the last two map entries and the first action. Not a criterion failure, but a real quality defect.

## The most important finding: the skill does not catch self-certification

Five of the six gate-gaming outputs contain a sentence certifying their own honesty inside the output itself:

- DEC-GG-01: *"Yellow+Red = 86%. Honest."*
- DEC-GG-02: *"I'd rather have one honest Red than three dramatic ones."*
- DEC-GG-04: *"No jargon found in scan."*
- DEC-GG-05: *"Calling these Red is not bravado."*
- DEC-GG-06: *"(this is the first thing produced — no plan, no encouragement)."*

The gates stop hollow output. They do not stop an output that announces it has passed. That is a subtler hollow — a compliance receipt instead of compliance — and the suite has no check for it. This is the clearest actionable gap the run found, and it is a skill defect, not a test defect.

## Test defects found by the judging pass

1. **The "Red count as evidence of honesty" ban lives in DEC-GG-02 alone.** DEC-GG-01's *"Yellow+Red = 86%. Honest."* walked straight past its own criteria. The constraint belongs in every triggering test, not one.
2. **"Every node carries X" is unfalsifiable** unless the record preserves every node. It did not. Either mandate full node text in the run record, or make the criteria countable ("at least 5 nodes each carry an observable pair").
3. **No test injects a polluted draft.** Nothing feeds the skill a plan containing "alive if the team works hard" and checks that the gates delete it. Free generation will not reliably produce the bad input the gates are built to reject. Check 1, 1b and 3b's *rejection* ability is currently untested.
4. **DEC-GG-03's "different band from its confidence would suggest" has no defined mapping.** Two independent scales, no stated correspondence — the criterion is vague, not strict.
5. **DEC-HP-03's fixture contains no plan** while its criteria require running the protocol against one. The test is unreachable as written. It also demands "an assumption with no survival condition" while the hard gate demands every node have one — self-locking under either reading.
6. **DEC-HP-04's criteria contradict its prompt.** The user says "we have a hunch but no falsifiable claim yet" and never says what the hunch is. No output can produce a master claim. Either put the hunch in the prompt, or score the *form* of the claim.
7. **DEC-HP-02 was not memory-isolated.** Its agent read this user's persistent memory and built the map around an inferred project. Realistic, but it measures the memory system as much as the skill.
8. **`evals/MANIFEST.yaml` still said `status: not-yet-run`** while this record claimed a completed run, and its target ("all 10 triggering tests pass on all three runs") cannot be met by one run.

## What this run does and does not establish

**Established:** the description separates its intended cases from its excluded ones; the output contract survives real generation; both regression fixes hold and propagate; the gates produce genuinely falsifiable survival conditions and specific first actions.

**Not established:** real-world trigger rate (agents were primed); that the gates reject deliberately bad input (never tested); multi-run stability (this is one draw, and the suite's own manifest asks for three).

**Recommended next:** a poisoned-draft test for Check 1/1b/3b; a global ban on self-certification in output; a countable form for the "every node" criteria; then three runs of the full suite.

## One new observation: self-certification is mode-dependent

The S1 defect — outputs certifying their own honesty — appeared in five of six generative runs (producing a map) and in **neither** poisoned-draft run (reviewing someone else's). When the task is adversarial review, the compliance receipts vanish.

That localises the defect: it is not that the model is dishonest, it is that the *output contract* invites a closing flourish when generating. The fix is a gate, not a personality change — say in the contract that the output ends at the first action, with nothing after it.
